## US-003: Sentence-translation typing — Levenshtein-3 tolerance
- started: 2026-05-19T02:47:30+0200
- finished: 2026-05-19T03:02:30+0200
- duration: ~15 minutes
- PR: #144 (squash-merged 0e612df6f4a46ab66c2d91e0406e9c3a7263aadf)
- Closes: #132
- What was implemented: TranslationTypingDrill now imports `levenshtein` from src/lib/server/levenshtein.ts directly and grades against `levenshtein(userNorm, canonicalNorm) <= 3`, picking the closest accepted canonical when the answer field carries multiple variants. Normalisation uses the shared `normaliseAnswer` helper (lowercase + trim + strip terminal punctuation + collapse whitespace). New `nearMiss` state surfaces a "Close enough — counted as correct." italic emerald hint only when correct && distance > 0; exact matches skip the hint so they're not visually demoted. Far-misses (>3) keep the existing wrong-answer feedback with the canonical revealed.
- Files changed: src/components/drills/TranslationTypingDrill.tsx, src/components/drills/__tests__/TranslationTypingDrill.test.tsx (new)
- Learnings:
  * The drill previously called `gradeText` (Levenshtein ≤1) which is correct for single-word listening-spell but wrong for sentence translation — the AC for this story is specifically the looser sentence tolerance, NOT a global threshold bump.
  * `parseField` does JSON.parse first then falls back to null on failure. Test fixtures MUST `JSON.stringify("ik wil een koffie")` even for plain strings, because a raw string isn't valid JSON; the production exercises table stores the answer as JSON.stringify(string) too. This bit me: first test run had all 5 assertion failures saying "expected true, got false" because canonicals[] was empty and bestDistance defaulted to Infinity.
  * `gh pr checks <n> --json state,conclusion` hits the well-known JSON parsing bug from `.ralph/patterns.md`; output is silently empty. Use `gh api repos/<owner>/<repo>/commits/<sha>/check-runs --jq '.check_runs[]'` instead and it returns clean output.
  * `gh api PUT ...` without the `-X PUT` flag form errors with "accepts 1 arg(s), received 2"; use `gh api -X PUT ...` (matches patterns.md note).
  * Distance verification by hand: "ik will een koffiess" vs "ik wil een koffie" = +1 ('l' insert) + 2 ('s','s' inserts) = 3. The test relies on that count.

- What was implemented: New `word_bank` drill type. `DrillType` union + hyphen normaliser cover `word_bank` (`word-bank` in seed). New WordBankDrill component (~230 LOC) with answer slot on top + shuffled tile bank below. Mobile-first ≥44×44px touch targets via `min-h-[44px] min-w-[44px]`. Distractor sourcing priority: `drill.options.distractors` first, then single-word `vocabPool` Dutch tokens (filtered to exclude canonical tokens and multi-word entries), capped at 3. Records via existing `recordDrillResult` per-exercise (the unit is the sentence, not the word pair). 2 sample word-bank exercises added to seed/exercises.json under a2-unit-1-werkwoorden-hebben-zijn.
- Files changed: src/lib/server/lesson.ts, src/components/drills/DrillRenderer.tsx, src/components/drills/WordBankDrill.tsx (new), src/components/drills/__tests__/WordBankDrill.test.tsx (new), seed/exercises.json
- Learnings:
  * The 44px touch-target rule (WCAG 2.5.5, iOS HIG) doesn't survive jsdom layout — there's no computed style. Assert via `className` regex (`min-h-[44px]` + `min-w-[44px]`) instead. Same trick should apply to any other mobile-first AC.
  * `parseField` JSON-parses, so a canonical sentence is stored as `JSON.stringify("ik wil een koffie")` (the same gotcha that bit US-003). The component handles both string and array-of-strings shapes so a future "accepted alternates" extension is one line away.
  * Distractor de-dup needs the case-folded key, but the displayed tile preserves original casing. Using `Set<lowercased>` + `uniq[]` preserves first-seen order while filtering duplicates — important because `vocabPool` can have e.g. "Ik" and "ik" both present and you don't want both leaking as tiles.
  * Multi-word `vocabPool.nl` entries (e.g. "ik heb") must be filtered out — otherwise the bank would surface a multi-token tile that the grader's space-split would treat as one chunk. Added `!nl.includes(" ")` to the filter chain and asserted it in the test.
  * `WordOrderingDrill` is conceptually adjacent but graded via Levenshtein-tolerant `gradeText`. We deliberately stayed strict (exact whitespace-normalised match) for word-bank because the bank only offers whole words, so typo tolerance has no surface to operate on.
